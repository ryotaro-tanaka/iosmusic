# AD-004: 再生制御API抽象の定義

- ID: AD-004
- タイトル: 再生制御API抽象の定義
- 日付: 2026-02-28
- ステータス: accepted

## 背景

再生実装は `react-native-track-player` を前提とするが、UI やユースケースがライブラリ実装に直接依存すると、仕様変更・差し替え・テスト時にコストが高くなる。

## 選択肢

1. 画面層/ユースケース層から再生ライブラリを直接呼ぶ
2. 再生 API の抽象インターフェースを定義し、アダプタ実装で接続
3. すべてネイティブモジュールに寄せる

## 決定

`PlayerService` 抽象を定義し、`react-native-track-player` は Infrastructure のアダプタで実装する。

想定 API（最小）:

- `setQueue(tracks)`
- `play(trackId)`
- `pause()`
- `seek(positionSec)`
- `getState()`
- `subscribeEvents(handler)`

## 採用理由

- Application 層を実装詳細から分離できる。
- モック実装でユニット/結合テストを行いやすい。
- 将来のライブラリ更新や差し替えの影響を局所化できる。

## 影響範囲

- 早期に `PlayerService` の契約（型・エラー仕様）を決める必要がある。
- イベント変換（ライブラリイベント → ドメインイベント）の実装が必要。

## リスク / トレードオフ

- 抽象化の分だけ初期実装が増える。
- ライブラリ固有機能を使う際に拡張設計が必要。

## 検証方法

- モック `PlayerService` で UseCase テストが成立することを確認。
- 実アダプタ差し替え時に UI/UseCase の変更が不要であることを確認。
