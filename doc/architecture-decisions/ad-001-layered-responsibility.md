# AD-001: レイヤ責務の分離方針

- ID: AD-001
- タイトル: レイヤ責務の分離方針
- 日付: 2026-02-28
- ステータス: accepted

## 背景

MVP では M1-1（一覧）から M3（復帰/復元）まで段階的に機能を広げるため、画面実装に再生ロジックやネイティブ依存が混在すると、後続マイルストーンで手戻りが増える。

## 選択肢

1. 画面中心（UI コンポーネントに再生制御・データ取得を集約）
2. 2層（UI + サービス）
3. 3層（Presentation / Application / Infrastructure）

## 決定

3層アーキテクチャを採用する。

- Presentation 層: 表示・入力・画面遷移のみを担当
- Application 層: ユースケース（再生、キュー更新、復元）を担当
- Infrastructure 層: 再生ライブラリ、ファイル探索、永続化など実装詳細を担当

## 採用理由

- 責務分離方針（画面 / アプリケーション / インフラ）が事前計画と整合する。
- M2 以降の BG 再生・割り込み対応で、UI とネイティブ実装を独立して進化させやすい。
- ユニットテストの対象を Application 層に集約できる。

## 影響範囲

- ディレクトリ構造と依存方向を明確化する必要がある。
- 画面層から Infrastructure 層を直接参照しない規約が必要。
- UseCase のインターフェース定義が初期に必要。

## リスク / トレードオフ

- 初期は実装量（抽象化・定義）が増える。
- 小規模変更でも層を跨ぐ修正が必要になる場合がある。

## 検証方法

- コードレビューで依存方向違反（Presentation → Infrastructure 直接依存）がないことを確認。
- UseCase 層のユニットテストで再生ロジックが UI 非依存で検証できることを確認。
