# 設計方針の事前意思決定（推奨）

MVP仕様とは別に、実装開始前に決めるべき設計方針をここに記録する。

## 目的

- 実装中の判断ブレを減らす
- M1からM4までの手戻りを減らす
- 役割分離とテスト観点を先に固定する

## 推奨ファイル構成

- `decision-log.md`: 意思決定一覧（要約）
- `decision-template.md`: 1件ごとの記録テンプレート

## 実装前に決めるべき主要項目

1. レイヤ責務（画面 / アプリケーション / インフラ）
2. 状態管理の境界（グローバル状態と画面ローカル状態）
3. ファイルアクセス方針（探索対象、エラー時挙動）
4. 再生制御APIの抽象（将来の差し替え可能性）
5. ログ方針（何をどこまで記録するか）
6. テスト戦略（どの層をユニット/結合/E2Eで担保するか）
7. Go/No-Go判定の運用（誰がいつ判定するか）

## 記録ルール

- 各決定は「背景 / 選択肢 / 採用理由 / 影響範囲」を必ず含める
- 決定変更時は「変更理由」を追記する

## 6つの設計方針（簡潔版）

### AD-001 レイヤ責務の分離方針
Presentation / Application / Infrastructure の3層で責務を分離する。
画面は表示と操作に専念し、再生やキュー更新はユースケースに集約する。
再生ライブラリやファイル探索などの実装詳細はインフラ層に閉じ込める。

### AD-002 状態管理の境界定義
再生状態・現在曲・キュー・再生位置はグローバルのドメイン状態として一元管理する。
一方で、モーダル開閉やフィルタ条件などの一時的 UI 状態は画面ローカルで管理する。
これにより BG/ロック画面操作時の不整合を防ぎ、画面の独立性も保つ。

### AD-003 ローカルM4A探索仕様
MVP では探索対象を M4A に限定し、探索フォルダを固定する。
探索失敗時はクラッシュさせず、ログ記録のうえ空配列を返す。
0件/1件/複数件をすべて正常系として扱い、M1-1 判定を明確にする。

### AD-004 再生制御API抽象の定義
`PlayerService` 抽象を先に定義し、実装は `react-native-track-player` アダプタで接続する。
UI とユースケースは抽象に依存し、ライブラリ実装に直接依存しない。
これによりテスト容易性と将来の差し替え耐性を確保する。

### AD-005 ログ/監視ポリシー
MVP では構造化ログ + 重要イベント最小セット + クラッシュ監視を採用する。
再生開始/停止、BG 継続可否、割り込み復帰、探索失敗などを優先記録する。
障害時に原因追跡できる観測性を、過剰な運用コストなしで確保する。

### AD-006 テスト戦略（ユニット/結合/E2E）
テストピラミッド（ユニット・結合・E2E）を採用し、DoD と連動させる。
ユニットでロジック、結合で層間連携、E2Eで端末依存挙動を担保する。
再生/シーク/BG継続/復帰の主要ユースケースを段階的に検証する。
