# 1.1 技術的調査（Feasibility）結果

最終更新: 2026-02-27

## 1. 調査目的と前提

`doc/pre-development-planning.md` の **1.1 可能かどうかの技術的な調査** に対して、以下を明文化する。

- MVP要件（ローカルM4A再生）で実現可能か
- バックグラウンド再生 / ロック画面連携 / オフライン再生を満たせる実装候補
- Go/No-Go判定に使う客観的な基準

> 注記: 現状リポジトリは Expo テンプレート構成だが、計画上の意思決定は Bare React Native 採用となっているため、本調査は **Bare RN 前提** で整理する。

## 1.1 確定事項（本調査の結論）

- **実装方式**: Bare React Native
- **使用ライブラリ**: `react-native-track-player`
- **採用理由**: iOS音楽アプリに必要なバックグラウンド再生・ロック画面/コントロールセンター連携・オフライン再生を満たしつつ、他候補より制約が少ないため。

## 2. 対象機能ごとの PoC 方針

### 2.1 バックグラウンド再生

- 検証内容
  - 画面OFF + バックグラウンド遷移後に 30 分連続再生
  - 途中でアプリを前面復帰しても再生状態が破綻しない
- 成功条件
  - 音切れ・停止なしで30分再生完了
  - 再生状態（playing/paused/position）がUIと同期

### 2.2 ロック画面 / コントロールセンター連携

- 検証内容
  - 再生/停止/次へ/前へのリモートコマンド
  - 曲名・アーティスト・アートワークの更新
- 成功条件
  - リモート操作成功率 100%（20回連続試行）
  - メタデータ更新遅延が体感上問題ない（< 1 秒目安）

### 2.3 オフライン再生（ローカルファイル）

- 検証内容
  - App Bundle内M4A、Documents配下M4Aの再生
  - キュー再生（3曲以上）とシーク
- 成功条件
  - ローカル参照失敗なし
  - シーク後も進行時間が正しく更新される

## 3. 採用候補比較（Bare RN 前提）

| 候補 | バックグラウンド再生 | ロック画面/リモート操作 | ローカルM4A | 保守性/実績 | 総評 |
|---|---|---|---|---|---|
| `react-native-track-player` | 強い（主要ユースケース想定） | 強い（Now Playing/Remote Command対応） | 対応可 | 音楽アプリ用途の実績が比較的多い | **第一候補** |
| `expo-av` / `expo-audio` | Bareでも利用可能だが運用設計に工夫が必要 | 標準での統合は限定的（要追加実装） | 対応可 | Expo文脈で情報は多い | Bare RN音楽アプリの中核にはやや不向き |
| `react-native-sound` | 限定的（効果音/単純再生向け） | 弱い（リモート制御は別実装前提） | 対応可 | 実装は軽いが機能不足 | MVP後半以降で詰まりやすい |

### 補足

- 本プロダクト要件（バックグラウンド + ロック画面連携）では、低レベル実装を自前で増やすほど不具合リスクと保守コストが増える。
- そのため「音楽プレイヤー機能が最初から揃うライブラリ」を優先した方が、PoC成功確率が高い。

## 4. iOS制約と対応可否チェック

### 必須設定（No-Goになりやすい項目）

1. Xcode Capability の Background Modes で `Audio, AirPlay, and Picture in Picture` を有効化
2. `AVAudioSession` のカテゴリを再生向け（例: `playback`）に設定
3. 割り込み（着信・他アプリ音声）ハンドリング
4. ロック画面メタデータ更新（Now Playing）
5. Remote Command ハンドラの登録（play/pause/next/previous）

### 判定

- 上記5項目を PoC で再現できない場合は **No-Go**。
- 1〜2項目を一時回避できても、恒久対応が難しい場合は **保留**（追加調査）。

## 5. 判断基準（Go/No-Go）

## 必須（Must）

- ローカルM4Aで再生/停止/シークが安定
- 30分バックグラウンド再生で停止しない
- ロック画面操作（再生/停止）が100%成功
- アプリ再起動後に最低限の再生状態を復元できる

## 望ましい（Should）

- 次へ/前へコマンド反映が1秒以内
- 割り込み復帰が期待通り（自動再開ポリシーが破綻しない）
- 実装が特定OSバージョン依存になりすぎない

## No-Go条件

- iOS設定が正しいにもかかわらず再現性のあるバックグラウンド停止
- リモート操作の取りこぼしが継続的に発生
- MVP時点でネイティブ改修が過剰（開発速度を著しく阻害）

## 6. 推奨結論（現時点）

- 採用ライブラリは **`react-native-track-player` で確定**。
- 理由は、バックグラウンド再生・ロック画面/コントロールセンター連携・オフライン再生という本プロダクト要件を満たし、他候補より実装上の制約が少ないため。
- この前提で 2〜3 日の PoC を実施し、Must 条件の達成をもって開発着手判断（Go）とする。
- MVPスコープは「ローカルM4A + 再生キュー + BG再生 + ロック画面基本操作」に固定し、形式追加や高度機能は後続マイルストーンに分離する。

## 7. 直近タスク（1.1完了のための作業）

1. PoCブランチ作成（audio-poc/track-player）
2. iOS capability / audio session 設定
3. 3曲キューで前面・バックグラウンド・ロック画面検証
4. 失敗ログと再現手順を記録
5. Go/No-Go判定を ADR 化


## 8. 実行方針（MVPを進めるか、検証を先に詰めるか）

結論としては、**MVP（ローカル M4A の再生/停止）を進めながら、撤退防止のための検証を先にゲート化して実施**する。

### 推奨アプローチ: 「ゲート付きMVP」

- Step 1（Day 1-2）
  - MVP最小実装: 前面で再生/停止/シーク
  - 同時に検証シナリオのうち「前面操作」を完了条件に設定
- Step 2（Day 3-4）
  - バックグラウンド 10分/30分連続再生を検証
  - ロック画面で再生/停止とメタデータ更新を検証
- Step 3（Day 5）
  - 割り込み復帰（着信相当）とアプリ再起動後の状態復元を検証
  - Go/No-Go を最終判断

### この進め方を推奨する理由

- いきなり全要件を実装すると、問題の切り分けが難しくなる。
- 逆にMVPだけ先行しすぎると、後半でバックグラウンド/ロック画面制約に詰まって手戻りが大きくなる。
- そのため「実装を止めずに、撤退ラインを先に判定できる順序」が最も安全。

### 進行判断ルール（運用）

- **継続条件**: 2.3 の検証シナリオが段階的に通過すること。
- **一時停止条件**: 30分バックグラウンド再生失敗、またはロック画面操作の再現性不足。
- **撤退/再設計条件**: 割り込み復帰・再起動復元が実現できず、恒久対応の見通しが立たない場合。
