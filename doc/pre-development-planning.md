# 開発前計画ガイド

最終更新: 2026-02-27

## 0. このプロジェクトで確定した意思決定

- **実装方式**: Expo ではなく **Bare React Native** を使用する。
  - 理由: バックグラウンド再生・ロック画面操作などのネイティブ制御を初期から確実に扱い、Expo Managed の制約を極力回避するため。
- **初期対応フォーマット**: **M4A のみ対応**（MVP段階）。
  - 理由: iOS との互換性が高く、実装・検証コストを抑えて要件検証を先行するため。

## 1. 開発前に最低限必要な3点

### 1.1 可能かどうかの技術的な調査（Feasibility）

- 調査結果ドキュメント: `doc/feasibility-investigation-1-1.md`
- 確定事項: Bare React Native + `react-native-track-player`（制約が少なく要件を満たすため）

- **対象機能ごとに PoC を作る**
  - バックグラウンド再生
  - ロック画面 / コントロールセンター連携
  - オフライン再生（ローカルファイル）
- **採用候補の比較表を作る（Bare RN 前提）**
  - 音声再生ライブラリ候補の機能差
  - iOS 制約（バックグラウンド・オーディオセッション）の対応可否
- **判断基準を明文化する**
  - 必須要件を満たすか
  - 実装コストと運用コストが許容範囲か

### 1.2 設計方針（責務分離・テスト方針）

- **責務分離の基本方針**
  - 画面層: 表示とユーザー操作のみ
  - アプリケーション層: ユースケース（再生、キュー更新など）
  - インフラ層: ストレージ/再生ライブラリの実装詳細
- **状態管理方針**
  - グローバル状態（再生状態、現在曲、キュー）
  - 画面ローカル状態（UI 表示用の一時状態）
- **テストピラミッド**
  - ユニット: 再生制御ロジック、キュー操作
  - 結合: ストア + ユースケース + リポジトリ
  - E2E: 再生開始、曲送り、復帰動作

### 1.3 開発スケジュール（ゲート付きMVPに更新）

- **マイルストーンを「実装 + 検証ゲート」単位で分割**
  1. **M1: 再生制御コア + 最小UI（前面確認）**
     - 実装: play/pause/seek、単曲再生、最小UI（再生/停止/シーク）
     - DoD(G1): 前面で再生/停止/シークが安定（クラッシュなし）
  2. **M2: BG再生/ロック画面連携**
     - 実装: バックグラウンド継続、Now Playing/リモートコマンド
     - DoD(G2): 10分/30分連続再生、ロック画面で再生/停止、メタデータ更新
  3. **M3: 割り込み復帰/状態復元**
     - 実装: 着信相当イベント対応、再起動後の再生位置/キュー復元
     - DoD(G3): 割り込み後復帰と再起動復元が再現可能
  4. **M4: 品質強化（テスト/自動化/計測）**
     - DoD: 主要ユースケースE2E通過、クラッシュ率目標以下

- **進行ルール**
  - G1未通過でM2に進まない
  - G2未通過でM3に進まない
  - G3未通過なら本開発スケールへ拡張しない（再設計判定）

## 2. Bare React Native での詰まりどころ（音楽アプリ向け）

### 2.1 詰まりやすい点

- **iOS の Audio Session/Background Mode 設定ミス**
  - 権限・Capabilities・セッションカテゴリ設定が不整合だと、バックグラウンドで停止しやすい。
- **ネイティブイベントの競合**
  - 再生状態更新、割り込み（着信/他アプリ音声）、リモートコマンド処理が競合しやすい。
- **保守コストの増加**
  - iOS/Android の差分吸収、ネイティブ依存更新、クラッシュ調査で工数が増える。

### 2.2 技術選定の実務的な進め方（推奨）

1. **PoC で先に「失敗条件」を確認する**
   - 画面 OFF・バックグラウンド・ロック画面操作・再起動復帰を検証する。
2. **Go/No-Go 判定を先に定義する**
   - 例: 「ロック画面で再生/停止が 100% 動作」「30分バックグラウンドで再生継続」
3. **初期スコープを固定する**
   - MVP はローカル M4A 再生に限定し、形式追加は後続フェーズで判断する。

### 2.3 最低限の検証シナリオ

- 実行順序の推奨: 「ゲート付きMVP」（詳細: `doc/feasibility-investigation-1-1.md` の「8. 実行方針」）

- アプリ前面: 再生/停止/シーク
- バックグラウンド遷移後: 10分/30分連続再生
- ロック画面: 再生/停止・メタデータ表示更新
- 割り込み: 着信相当イベント後の自動復帰
- 復帰: アプリ再起動後の再生位置・キュー復元

## 3. 追加で必要な項目（おすすめ）

### 3.1 プロダクト要件の定義

- ペルソナ、利用シーン、優先ユースケース
- MVP に含める/含めない機能の線引き
- 非機能要件（起動時間、オフライン挙動、バッテリー消費）

### 3.2 運用設計

- ログ・監視・クラッシュレポート基盤
- 障害対応フロー（検知→一次切り分け→復旧）
- リリース後の指標（継続率、再生完了率など）

### 3.3 品質保証プロセス

- ブランチ戦略とレビュー基準
- CI での必須チェック（lint/typecheck/test）
- 回帰確認リスト（再生中断、バックグラウンド復帰など）

### 3.4 セキュリティ / 法務 / ストア申請観点

- 収集データとプライバシーポリシー整備
- 著作権・配信ライセンスの整理（必要時）
- App Store 申請要件（権限説明、審査観点）

### 3.5 チーム運営ルール

- 意思決定の記録（ADR: Architecture Decision Record）
- ドキュメント更新責任者の明確化
- 定例での計画見直し（例: 週次）

## 4. 最初の2週間でやること（例）

- **Day 1-2**: 要件整理、MVP 定義（Bare RN + M4A 限定）
- **Day 3-5**: 技術 PoC（BG再生/ロック画面連携）
- **Week 2 前半**: アーキテクチャ設計、テスト戦略決定
- **Week 2 後半**: タスク分解、見積もり、開発開始
