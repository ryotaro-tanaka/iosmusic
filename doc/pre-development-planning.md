# 開発前計画ガイド

最終更新: 2026-02-26

## 1. 開発前に最低限必要な3点

### 1.1 可能かどうかの技術的な調査（Feasibility）

- **対象機能ごとに PoC を作る**
  - バックグラウンド再生
  - ロック画面 / コントロールセンター連携
  - オフライン再生（キャッシュ/ダウンロード）
- **採用候補の比較表を作る**
  - `expo-av` と専用ライブラリの機能差
  - iOS 制約（バックグラウンド・オーディオセッション）の対応可否
- **判断基準を明文化する**
  - 必須要件を満たすか
  - 実装コストと運用コストが許容範囲か

### 1.2 設計方針（責務分離・テスト方針）

- **責務分離の基本方針**
  - 画面層: 表示とユーザー操作のみ
  - アプリケーション層: ユースケース（再生、キュー更新など）
  - インフラ層: API/ストレージ/再生ライブラリの実装詳細
- **状態管理方針**
  - グローバル状態（再生状態、現在曲、キュー）
  - 画面ローカル状態（UI 表示用の一時状態）
- **テストピラミッド**
  - ユニット: 再生制御ロジック、キュー操作
  - 結合: ストア + ユースケース + リポジトリ
  - E2E: 再生開始、曲送り、復帰動作

### 1.3 開発スケジュール

- **マイルストーンを機能単位で分割**
  1. MVP（ローカル音源で再生/停止/曲送り）
  2. ライブラリ管理（一覧・検索・プレイリスト）
  3. バックグラウンド再生/通知連携
  4. 品質強化（テスト、自動化、計測）
- **各マイルストーンに完了条件（DoD）を設定**
  - 例: 「主要ユースケースが E2E で通る」「クラッシュ率目標以下」

## 2. Expo / 素の React Native の詰まりどころ（音楽アプリ向け）

> 結論: **Expo でも素の RN でも詰まる可能性はある**。ただし、詰まるポイントと回避手段が異なる。

### 2.1 Expo で詰まりやすい点

- **Managed Workflow の制約**
  - 使用したいネイティブ機能が Expo SDK/Config Plugin で十分に扱えない場合、実装が止まりやすい。
- **ロック画面操作の要件差分**
  - 単純再生は可能でも、細かいメタデータ更新やリモートコマンド対応で要件を満たせないケースがある。
- **依存ライブラリ更新の追従**
  - Expo SDK とライブラリの互換性タイミングが合わないと、採用候補が限定される。

### 2.2 素の React Native（Bare）でも詰まりやすい点

- **iOS の Audio Session/Background Mode 設定ミス**
  - 権限・Capabilities・セッションカテゴリ設定が不整合だと、バックグラウンドで停止しやすい。
- **ネイティブイベントの競合**
  - 再生状態更新、割り込み（着信/他アプリ音声）、リモートコマンド処理が競合しやすい。
- **保守コストの増加**
  - iOS/Android の差分吸収、ネイティブ依存更新、クラッシュ調査で工数が増える。

### 2.3 技術選定の実務的な進め方（推奨）

1. **PoC で先に「失敗条件」を確認する**
   - 画面 OFF・バックグラウンド・ロック画面操作・再起動復帰を検証する。
2. **Go/No-Go 判定を先に定義する**
   - 例: 「ロック画面で再生/停止/曲送りが 100% 動作」「30分バックグラウンドで再生継続」
3. **段階的移行を前提にする**
   - 最初は Expo で進め、要件不足が確定した時点で Bare へ移行する判断基準を ADR 化する。

### 2.4 最低限の検証シナリオ

- アプリ前面: 再生/停止/シーク/曲送り
- バックグラウンド遷移後: 10分/30分連続再生
- ロック画面: 再生/停止/前後曲・メタデータ表示更新
- 割り込み: 着信相当イベント後の自動復帰
- 復帰: アプリ再起動後の再生位置・キュー復元

### 2.5 「最初から Bare RN で書くべきか？」の判断軸

- **結論（実務寄り）**
  - 要件が「高度なバックグラウンド再生 + リモートコマンド + 複雑なネイティブ制御」を**初期から必須**とするなら、最初から Bare RN を選ぶ合理性は高い。
  - ただし、要件がまだ流動的で MVP 検証を優先するなら、Expo で始めて移行条件を先に固定する方が総工数が小さい場合がある。
- **Bare RN を先に選ぶべき条件**
  - iOS/Android のネイティブ実装差分を早期に詰める必要がある。
  - 採用予定ライブラリが Expo Managed では実質運用困難。
  - チーム内にネイティブ運用（Xcode/Gradle/CI）を回せる体制がある。
- **Expo 先行が有効な条件**
  - まず UX・情報設計・主要ユースケースの検証を短期間で回したい。
  - ネイティブ深掘りは 2nd フェーズで十分。
  - 開発体験と配布フロー（OTA 含む）を重視する。

### 2.6 Expo の利点は「初速」だけか？

- **初速以外の実務メリットもある**
  - **開発運用の標準化**: 設定・ビルド・配布の共通化により、オンボーディングコストを下げやすい。
  - **アップデート運用**: OTA 更新など、軽微修正の反映フローを組みやすい。
  - **周辺機能との統合**: Expo の提供機能（通知、権限、デバイス API など）を一貫した流儀で扱いやすい。
- **一方で限界も明確**
  - ネイティブ拡張が主戦場になるほど、Managed の制約や互換性待ちがボトルネックになりやすい。
  - したがって「Expo か Bare か」は優劣ではなく、**現在フェーズの最適化問題**として扱う。

### 2.7 推奨意思決定ルール（このプロジェクト向け）

- **Rule 1**: まず Expo で 1 週間以内の PoC を実施し、以下を満たせなければ Bare 検討に進む。
  - ロック画面操作（再生/停止/曲送り）が安定。
  - 30 分バックグラウンド再生が安定。
  - 復帰時の状態不整合が許容範囲。
- **Rule 2**: Bare 移行時は「移行コスト」と「得られる要件充足」を ADR に定量記録する。
- **Rule 3**: どちらを選んでも、検証シナリオと完了条件（DoD）は共通化する。

## 3. 追加で必要な項目（おすすめ）

### 3.1 プロダクト要件の定義

- ペルソナ、利用シーン、優先ユースケース
- MVP に含める/含めない機能の線引き
- 非機能要件（起動時間、オフライン挙動、バッテリー消費）

### 3.2 運用設計

- ログ・監視・クラッシュレポート基盤
- 障害対応フロー（検知→一次切り分け→復旧）
- リリース後の指標（継続率、再生完了率など）

### 3.3 品質保証プロセス

- ブランチ戦略とレビュー基準
- CI での必須チェック（lint/typecheck/test）
- 回帰確認リスト（再生中断、バックグラウンド復帰など）

### 3.4 セキュリティ / 法務 / ストア申請観点

- 収集データとプライバシーポリシー整備
- 著作権・配信ライセンスの整理（必要時）
- App Store 申請要件（権限説明、審査観点）

### 3.5 チーム運営ルール

- 意思決定の記録（ADR: Architecture Decision Record）
- ドキュメント更新責任者の明確化
- 定例での計画見直し（例: 週次）

## 4. 最初の2週間でやること（例）

- **Day 1-2**: 要件整理、MVP 定義
- **Day 3-5**: 技術 PoC、採用技術決定
- **Week 2 前半**: アーキテクチャ設計、テスト戦略決定
- **Week 2 後半**: タスク分解、見積もり、開発開始
